# ResourceManager and Ranger Admin HA Baseline

This document covers the entry points, four-step wizards, configuration transformations, background tasks, Kerberos integration, failure recovery, and backend interfaces for ResourceManager HA (RM HA) and Ranger Admin HA (RA HA) in the legacy Ember frontend. It is the behavior baseline for the React frontend; the presence of a page with the same name is not feature parity.

The scope explicitly excludes Metrics displays, charts, Widgets, and metric queries. Host CPU, memory, and disk fields appearing here are used only for HA host selection and are not Metrics display functionality.

Evidence labels follow [00-methodology.md](00-methodology.md): `CONFIRMED` means that at least two types of static evidence corroborate each other; `CONDITIONAL` means that behavior depends on permission, stack, service, or security mode; `STATIC_ONLY` means that a static path exists but must not be claimed to be runtime-available; `NEEDS_RUNTIME_VALIDATION` means that the behavior must be verified on a real cluster before React comparison.

### ResourceManager Configuration Contract

The following is the complete property set displayed in Review and overwritten by Step 4. All of these properties are read-only and cannot be overridden in Review; `rm1` always refers to the currently installed RM and `rm2` to the new RM.

| ID | Site | Exact property and value | Source, conditions, and compatibility boundaries |
| --- | --- | --- | --- |
| RMHA-CFG-001 | `yarn-site` | `yarn.resourcemanager.ha.enabled=true` | The source value is boolean `true` |
| RMHA-CFG-002 | `yarn-site` | `yarn.resourcemanager.ha.rm-ids=rm1,rm2` | IDs are fixed and are not renamed by existing configuration or Advisor |
| RMHA-CFG-003 | `yarn-site` | `yarn.resourcemanager.hostname.rm1=<currentRM>`; `yarn.resourcemanager.hostname.rm2=<additionalRM>` | Hostnames only; no ports are appended |
| RMHA-CFG-004 | `yarn-site` | `yarn.resourcemanager.resource-tracker.address.rm1=<currentRM>:<port>`; `.rm2=<additionalRM>:<port>` | Takes the port after the colon from the old `yarn.resourcemanager.resource-tracker.address`; defaults to `8025` when missing |
| RMHA-CFG-005 | `yarn-site` | `yarn.resourcemanager.webapp.address.rm1=<currentRM>:<port>`; `.rm2=<additionalRM>:<port>` | Takes the port from the old `yarn.resourcemanager.webapp.address`; defaults to `8088` when missing |
| RMHA-CFG-006 | `yarn-site` | `yarn.resourcemanager.webapp.https.address.rm1=<currentRM>:<port>`; `.rm2=<additionalRM>:<port>` | Takes the port from the old `yarn.resourcemanager.webapp.https.address`; defaults to `8090` when missing |
| RMHA-CFG-007 | `yarn-site` | `yarn.resourcemanager.recovery.enabled=true` | The source value is boolean `true` |
| RMHA-CFG-008 | `yarn-site` | `yarn.resourcemanager.store.class=org.apache.hadoop.yarn.server.resourcemanager.recovery.ZKRMStateStore` | Fixed implementation class |
| RMHA-CFG-009 | `yarn-site` | `yarn.resourcemanager.zk-address=<zk1>:<port>,<zk2>:<port>,...` | Uses all `ZOOKEEPER_SERVER` master mappings; port comes from `zoo.cfg/clientPort`, defaulting to `2181`; does not filter runtime state or maintenance |
| RMHA-CFG-010 | `yarn-site` | `yarn.resourcemanager.cluster-id=yarn-cluster` | Fixed value |
| RMHA-CFG-011 | `yarn-site` | `yarn.resourcemanager.ha.automatic-failover.zk-base-path=/yarn-leader-election` | Fixed value |
| RMHA-CFG-012 | `yarn-client` | `yarn.resourcemanager.ha=<currentRM>:8032,<additionalRM>:8032` | Generated, displayed, and saved only when HAWQ is installed |
| RMHA-CFG-013 | `yarn-client` | `yarn.resourcemanager.scheduler.ha=<currentRM>:8030,<additionalRM>:8030` | Generated, displayed, and saved only when HAWQ is installed |
| RMHA-CFG-014 | `core-site` | `hadoop.proxyuser.<yarn_user>.hosts=<Advisor value>` | Added to the save set only when both `yarn-env/yarn_user` and the Advisor recommendation exist; the host value computed by the wizard initializer itself is not added directly to the form |
| RMHA-CFG-015 | Three sites | Merges into the current complete `yarn-site`, conditional `yarn-client`, and complete `core-site`, respectively, then creates new desired config versions | The three sites are independent serial PUT requests, not a transaction; old generic address properties without `.rm1/.rm2` are not explicitly deleted, and the wizard does not generate additional suffixed RM client/admin/scheduler address properties |

## Shared Failure, Recovery, and Kerberos Semantics

| ID | Level | Function and behavior | Key boundaries | Primary evidence |
| --- | --- | --- | --- | --- |
| HA-COMMON-FAIL-001 | `CONFIRMED` | The Step 4 task state machine is `PENDING -> QUEUED -> IN_PROGRESS -> COMPLETED/FAILED`; only one unfinished task advances at a time | Does not start later tasks when any task is `FAILED/QUEUED/IN_PROGRESS`; an API error directly marks the current task FAILED | `wizardProgressPageController.js#statusChangeCallback/#onTaskError` |
| HA-COMMON-FAIL-002 | `CONFIRMED` | Polls the request every 4 seconds and aggregates results after all backend tasks leave `PENDING/QUEUED/IN_PROGRESS` | Any server task in `FAILED/TIMEDOUT/ABORTED` marks the entire UI task FAILED; otherwise it is COMPLETED | progress mixin `POLL_INTERVAL/#parseLogs` |
| HA-COMMON-FAIL-003 | `CONFIRMED` | Clicking a task title opens the host/task progress popup with host-aggregated tasks and stdout/stderr/output/error logs | Opens only for IN_PROGRESS/FAILED/COMPLETED tasks with a request ID; task details continue polling to a terminal state | HA progress popup controller, common progress template |
| HA-COMMON-FAIL-004 | `CONFIRMED` | Retry selects only the first FAILED task, clears Retry/Rollback UI, and resets it to PENDING | COMPLETED tasks are not replayed; after this task succeeds, later PENDING tasks continue in original order | progress mixin `retryTask` |

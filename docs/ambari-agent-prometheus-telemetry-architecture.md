# Ambari Agent Prometheus Telemetry Architecture

## Overview

Ambari Agent contains a small Prometheus exporter for Linux host metrics and a
bounded, route-based proxy for metrics exposed by managed components on the
same host. Ambari Server remains the source of truth for topology, Stack
metadata, effective configuration, protocol, port, and Kerberos settings.

The implementation separates configuration distribution from metric values:

```text
Control plane

  Stack telemetry.json + JMX profiles
                  |
                  v
  Ambari Server assignment compiler (topology + effective configuration)
                  |
       STOMP telemetry-v1 assignment
                  |
                  v
  Agent last-known-good configuration cache

Data plane

  Ambari HTTP SD --> vmagent --> Agent /metrics ----------------> Linux collectors
                           |
                           +--> /metrics/components/{routeId}
                                      |
                                      +--> native /prom pass-through
                                      +--> /jmx typed conversion
                           |
                           +-- remote write --> VictoriaMetrics

  React monitoring UI --> Ambari query proxy --> VictoriaMetrics datasource
```

The Agent persists only the current assignment and content-addressed JMX
profiles. Every component response is fetched and validated during the
corresponding vmagent scrape. The Agent does not cache previously scraped
metric values, aggregate samples across scrapes, or send samples in heartbeat
payloads.

## Agent Exporter

The exporter is configured in `ambari-agent.ini`:

```ini
[prometheus]
enabled=true
bind_address=0.0.0.0
port=9101
```

It is enabled by default on Linux and can be disabled explicitly. A malformed
or out-of-range port falls back to 9101, and a bind failure is contained in the
exporter thread rather than terminating Ambari Agent.

The HTTP surface is:

| Path | Purpose |
| --- | --- |
| `/metrics` | Linux host metrics and exporter self-metrics |
| `/metrics/components/{routeId}` | One assigned component target |
| `/-/healthy` | Exporter process health |

Host collectors read Linux `/proc` and `statvfs` data. The bounded host metric
contract covers:

* CPU time and logical CPU count;
* memory, swap, load, uptime, boot time, process states, and aggregate process
  thread count;
* filesystem capacity and inodes, disk operations and throughput, and network
  packets, throughput, errors, and drops;
* context switches, interrupts, file-descriptor allocation, available entropy,
  OOM kills, conntrack usage, and TCP connections by a fixed state set.

Optional kernel files are omitted independently when the running kernel does
not expose them. The aggregate `ambari_agent_process_threads` gauge sums field
20 from readable `/proc/<pid>/stat` records but does not export per-process
identity. The collectors introduce no unbounded process, command-line, socket,
user, or container labels. Collector failures are isolated so one unavailable
source does not suppress the remaining host metrics. Generic device-error
inference is outside this contract because Linux `/proc` does not provide a
reliable cross-device source.

Each component route has an independent upstream request and failure result.
The route ID is generated by Ambari Server and cannot be used to select an
arbitrary URL. Requests to unknown or nested route paths return 404.

## Component Routes

The initial BIGTOP 3.2.0 Stack integration covers seven components:

| Service component | Upstream | Agent handling | Contract evidence |
| --- | --- | --- | --- |
| HDFS NameNode | `/prom` | Validate and pass through | Live `/prom` capture |
| HDFS DataNode | `/prom` | Validate and pass through | Live `/prom` capture |
| YARN ResourceManager | `/prom` | Validate and pass through | Live active/standby `/prom` captures and Hadoop 3.3.6 source contract |
| YARN NodeManager | `/jmx` | Typed JMX conversion | Hadoop 3.3 profile and conversion fixture |
| HBase Master | `/jmx` | Typed JMX conversion | HBase 2.4 profile and conversion fixture |
| HBase RegionServer | `/jmx` | Typed JMX conversion | HBase 2.4 profile and conversion fixture |
| HiveServer2 | `/jmx` | Typed JMX conversion | Hive 3.1 profile and conversion fixture |

`hadoop.prometheus.endpoint.enabled=true` enables the Hadoop native endpoint.
NodeManager deliberately does not use it in the Hadoop 3.3 Stack contract. The
in-process Timeline Collector can register the global Prometheus sink before
the fixed NodeManager Web UI, leaving the stable Web UI `/prom` endpoint empty.
The assignment therefore uses the stable NodeManager Web UI `/jmx` endpoint.

Native output retains the component's own metric names and labels. JMX profiles
select explicit ObjectNames and numeric attributes, apply typed names and unit
conversion, enforce counter `_total` suffixes, and cap output series. Dynamic
ObjectNames are not exported as labels unless a profile explicitly declares a
bounded label source.

The validation evidence is intentionally scoped. NameNode, DataNode, and both
active and standby ResourceManager native metric names and types were checked
against live `/prom` captures on 2026-08-28. ResourceManager types were also
checked against the Hadoop 3.3.6 `PrometheusMetricsSink` naming algorithm and
metric source definitions. The four JMX routes are checked with captured JSON
fixtures and profile conversion tests. Raw native capture files remain local
validation artifacts and are not packaged in the repository.

## Stack Contract

A service opts in through `telemetry.json`. The descriptor maps a component to
an upstream format, path, effective-config references, optional HA property
prefixes, timeout and response bounds, and an optional JMX profile. It is
loaded through the existing Stack service inheritance path.

`metrics.json` is no longer a time-series monitoring contract. It contains only
the small direct-JMX control-plane set required by management workflows:

| Component | Retained attributes |
| --- | --- |
| NameNode | `HAState`, `ClusterId`, `Safemode`, `LastCheckpointTime`, `JournalTransactionInfo` |
| JournalNode | `JournalsStatus` |
| HBase Master | `IsActiveMaster`, `liveRegionServers`, `deadRegionServers` |

These point-in-time values support HA role, safe mode, cluster identity,
checkpoint, and active-master decisions. They are not stored in
VictoriaMetrics and are not queried by monitoring dashboards.

`telemetry.json` and its typed JMX profiles are the monitoring data-plane
contract. They describe scrape transport and Prometheus conversion without
coupling collection to a storage implementation.

The Server validates both descriptors and profiles before assigning them. It
resolves the effective host configuration, uses the component host name as the
destination, extracts only the configured port, selects HTTP or HTTPS from the
Stack policy, resolves HA-suffixed properties, and substitutes `_HOST` in
Kerberos principals.

## Assignment Lifecycle

For each Agent host, Ambari Server compiles a complete assignment sorted by a
stable route ID. JMX profiles are canonicalized and addressed by SHA-256. The
complete event receives the existing Agent data-holder hash and is delivered
over the `telemetry-v1` STOMP capability.

The Server refreshes assignments for cluster configuration changes, component
install/uninstall events, host registration/removal, and completed Stack
upgrades. Registration performs an immediate hash comparison. The Agent also
reconciles its current hash every five minutes so a missed event recovers
without restarting either process.

The Agent validates a complete candidate bundle before activation. Profile
files and the assignment envelope are written with a temporary file, `fsync`,
and atomic rename while one update lock serializes STOMP and reconciliation
updates. Invalid or incomplete updates leave the previous in-memory and
on-disk assignment active. At startup, only referenced profiles with matching
digests are loaded.

## Scrape Processing

Native Prometheus responses must be non-empty UTF-8 text with at least one
sample and no malformed sample lines. The Agent does not rename or merge
native families.

JMX responses must contain a JSON `beans` array. ObjectNames are parsed into a
domain and quoted key properties; profiles match these structured fields.
Only finite numeric or Prometheus-supported special values are rendered.
Missing attributes omit individual samples. A response with no profile match,
duplicate output series, invalid JSON, or too many series fails that route.

Each route has a nonblocking concurrency semaphore, a request timeout, a
response-size limit, and redirect rejection. Over-limit requests return 503;
upstream, authentication, validation, and conversion failures return a non-2xx
response so Prometheus records the target as down. Other component routes and
the host exporter remain available.

## Security

The exporter has no application-level authentication and is enabled by default
on Linux. Deployments must bind it to a monitoring interface or enforce access
with host firewall policy. Ambari Server service discovery requires the
`CLUSTER.VIEW_METRICS` authorization.

Assignments accept only HTTP or HTTPS URLs without credentials, query strings,
or fragments. They contain local keytab paths and resolved principals when the
cluster uses Kerberos, never keytab contents or passwords. SPNEGO requests use
the existing Agent Kerberos cache helper with redirects disabled, HTTP errors
enabled, bounded response size, and TLS verification. The configured Agent CA
file is inherited when a route does not provide a dedicated CA path.

## Service Discovery

vmagent obtains Prometheus HTTP service-discovery targets from:

```text
GET /api/v1/clusters/{cluster}/prometheus_targets
```

The endpoint returns one target group for every host exporter and component
route. A component group has authoritative `cluster`, `host`, `service`,
`component`, and `ambari_target="component"` labels. A host group has
`cluster`, `host`, and `ambari_target="host"`; it intentionally has no service
or component identity. `__metrics_path__` selects `/metrics` or the independent
component route.

The managed vmagent metric allowlist keeps host samples only when the target
identity and metric family match `host;;ambari_agent_.*`. Component families
have separate component-specific allowlist entries. This prevents native
component output or an identically named upstream label from being mistaken
for host telemetry. Built-in Linux dashboard queries therefore scope every
host selector with both `cluster="${cluster}"` and `ambari_target="host"`.

The rendered discovery configuration is cached by the source assignment
hashes, includes an ETag, and uses a short private revalidation window. This is
configuration caching, not metric-value caching. The configured
`prometheus.agent.metrics.port` on Ambari Server must match the Agent exporter
port on every host.

The managed vmagent scrape template uses:

```yaml
scrape_configs:
  - job_name: ambari-prometheus-targets
    honor_labels: false
    http_sd_configs:
      - url: https://ambari.example.com:8443/api/v1/clusters/cluster1/prometheus_targets
        basic_auth:
          username: prometheus
          password_file: /etc/prometheus/ambari-password
```

`honor_labels: false` ensures that the HTTP SD labels win if an upstream
exporter emits a conflicting label. The vmagent `external_labels` value
`ambari_cluster` is separate metadata and is not the dashboard isolation key;
queries use the authoritative `cluster` label. The HTTP SD identity needs only
`CLUSTER.VIEW_METRICS`. TLS and Ambari authentication follow vmagent's
Prometheus-compatible `http_sd_config` behavior.

vmagent remote-writes samples to the single-node VictoriaMetrics endpoint or,
for a clustered deployment, to `vminsert`. An optional `vmauth` endpoint can
front writes and queries. vmagent's local remote-write queue is delivery
buffering after a scrape; it does not change the Agent's no-value-cache
contract.

VictoriaMetrics `replication_factor` controls copies written across VMSTORAGE
nodes. The separate vmagent scrape replication factor controls how many
vmagent members scrape each target and is limited to two by the Agent route
concurrency contract. When scrape replication is two, managed storage uses the
scrape interval as its deduplication interval.

## Query And Dashboard Path

Ambari Server stores cluster-scoped datasource definitions and provides a
bounded Prometheus-compatible query proxy. The React client calls Ambari's
`/metrics/{datasourceId}/api/v1/query` and `query_range` endpoints; browser
clients do not need direct VictoriaMetrics network or credential access. When
the managed VictoriaMetrics service is installed without VMAUTH
authentication, Ambari provisions a default VictoriaMetrics datasource. Other
authentication topologies can use an explicitly configured datasource.

The React monitoring UI renders packaged and user-created dashboards. Eleven
built-in dashboards cover HDFS, NameNode, DataNode, HBase Master, HBase
RegionServer, HiveServer2, NodeManager, ResourceManager, ResourceManager host
metrics, and two Linux host workflows:

| Dashboard | Scope | Host selection |
| --- | --- | --- |
| Linux Fleet Overview | Cluster-wide inventory, capacity, utilization, and Top-N host signals | All HTTP SD host targets in the current cluster |
| Linux Host Detail | CPU, memory, load, filesystem, disk, network, process, and kernel detail | Text variable `host`, default `.*`, applied as `host=~"${host}"` |

Both Linux dashboards are available at the React Dashboard metrics location.
Their queries use `ambari_agent_*` families directly and always include the
authoritative `cluster="${cluster}",ambari_target="host"` target scope. No
legacy Categraf, Telegraf, or AMS aliases are emitted.

The four source templates `categraf-processes.json`,
`host_generic_categraf.json`, `linux_by_categraf.json`, and
`linux_by_telegraf_overview.json` are semantic migration inputs, not packaged
compatibility dashboards. Their useful host-monitoring signals are consolidated
into the fleet and host-detail workflows. Their duplicate layouts, old metric
names, and Categraf or Telegraf assumptions are not retained.

Packaged panels group only targets with the same physical dimension. Byte
gauges use `bytesIEC`, byte rates use `bytesSecIEC`, durations use `seconds`,
0..1 ratios use `percentUnit`, and event or request rates use `cps` or `reqps`.
MiB-valued Hadoop ResourceManager metrics are converted to bytes before
display. Static dashboard contracts verify query counts, metric types, label
scope, dynamic rate windows, display units, and known source scaling.
HBase cluster-level Master panels join against the typed
`hbase_master_active` gauge so standby Master state cannot enter cluster
aggregates; process and JVM panels intentionally remain visible per host.

Before every panel query, the React client overwrites any dashboard-supplied
`cluster` variable with the current `AppContext.clusterName`, escaped as a
Prometheus label value. It also computes
`$__rate_interval = max(4 * query_step, 120s)`. The 120-second floor is four
times the managed vmagent default 30-second scrape interval. Packaged counter
queries use `rate` or `increase` with `[$__rate_interval]`; gauges are queried directly.
The `cluster` and `__rate_interval` variables are reserved and are not exposed
as editable dashboard variables. The same cluster binding is applied when a
panel is shared.

## Operational Metrics

The host `/metrics` endpoint reports exporter state including configured
routes, requests by route and result, last scrape duration, last successful
scrape timestamp, JMX conversion failures, configuration reload status, and
host collector health and duration.

These metrics distinguish an Agent exporter failure from an upstream component
failure. Prometheus `up` remains the authoritative end-to-end scrape result for
each independently discovered target.

## Removed And Retained Boundaries

The runtime monitoring path removes these legacy subsystems:

* Ambari Metrics System collector/monitor services, temporal property
  providers, sinks, service commands, Stack dependencies, and their tests and
  fixtures;
* Ganglia services, integrations, configuration, and tests;
* the AMS-backed legacy `Widget`, `WidgetLayout`, and active-widget REST,
  provider, persistence, descriptor, authorization, and test model.

The React `Board`, `Dashboard`, and `Datasource` model is the replacement for
the removed dashboard widget model. The new `ambari-metrics` distribution
module packages VictoriaMetrics and does not restore the old AMS runtime.

The following similarly named features are outside that deletion boundary and
remain supported:

* direct JMX/REST providers, `MetricsRetrievalService`, JMX alerts, and the
  minimal `metrics.json` control-plane values described above;
* Hadoop YARN Timeline Service, which is a Hadoop component rather than the AMS
  Timeline Metrics collector;
* service Theme configuration widgets, which are form controls rather than
  monitoring dashboards.

`ambari-web/classic` is outside this migration and is not part of the supported
React monitoring path.

## Compatibility And Limits

The implementation does not emit aliases for previous Categraf or Telegraf
metric names. Ambari provisions its own React dashboards, not Grafana
dashboards or recording rules. Host collectors intentionally favor stable,
low-cardinality operating-system signals over parity with every third-party
collector plugin. HBase 2.6+ native `/prometheus` support can replace JMX only
after its version-specific output and authentication behavior are verified.
Windows keeps the exporter disabled because the initial host collectors
require Linux `/proc`.
